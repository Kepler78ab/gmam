# module_tcp 待核查注意事项（直接复制给AI‑IDE做代码审查）
> 背景：模块新增API：`clearReceiveBuffer()`、`receiveBufferSize()`；文档新增帧失步与上层重同步章节。请结合源码核查下面全部要点。

## 一、新增接口线程安全核查（最高优先级）
1. `void clearReceiveBuffer()`
- 接收缓冲区运行在独立工作worker子线程；**禁止主线程直接读写worker内部buffer成员**。
- 该接口必须是`slot`，内部通过`invokeMethod`/信号槽把清空动作投递到worker线程异步执行。
- 函数返回不代表缓冲已经清空，是异步操作。
- 行为约束：**只清空接收拆帧buffer；绝对不能修改发送队列、不能重置wait‑ack等待状态、不改变TCP连接状态**。

2. `int receiveBufferSize() const`
- worker在子线程，读取buffer size是跨线程快照；
- 返回值仅用于诊断告警，**不可以作为业务逻辑判断条件**；
- worker未启动/未运行时应当返回0；
- 注意时序延迟：调用拿到的是过去某一时刻的数值，不是实时强一致。

## 二、`clearReceiveBuffer()` 在wait‑ack开启时的行为
- 当`ackEnabled=true`，正在wait应答的状态下调用`clearReceiveBuffer()`：接收buffer被清空，尚未参与matcher匹配的应答帧直接丢失；会触发ack超时、执行重传逻辑。
- 代码不需要修改逻辑，但要确认该行为客观存在，API注释、文档需要写明这个副作用。

## 三、原有弱自愈逻辑边界确认
模块内置两个弱自愈（不是可靠重同步）：
1. 解析帧头/长度非法：滑1字节，循环继续尝试解析；
2. 报文超过`maxFrameSize`：清空接收buffer并抛错误。

核查：
1. 确认**滑1字节逻辑不会向上报专门的“帧失步”信号**；它属于尽力而为兜底，模块不保证一定恢复同步。
2. 不能把滑1字节当做工业业务可用的重同步方案，文档已经注明，代码层面不要强化这个能力。
3. 只有超过`maxFrameSize`才自动清空buffer；普通乱码、非法长度不会自动清空。

## 四、断开连接时buffer处理
- `disconnected`触发（正常断开、异常断开），模块内部必须自动清空接收拆帧buffer。
- 重连之后buffer初始为空，不会携带上一次会话残片；该逻辑要确认各代码分支都走到，无漏分支。

## 五、API使用逻辑边界（业务侧约束，代码+文档对齐）
1. `frameReceived`输出的帧，仅代表**语法拆帧完整**，**不等于业务语义合法**；业务必须做校验（魔数、CRC、事务ID、长度语义等）。
2. 不建议业务单帧校验失败就直接调用`clearReceiveBuffer()`；推荐业务维护连续失败计数器，连续N帧校验失败才触发盲重置。
3. 两种重同步选型：
    - Modbus‑TCP这类无固定帧魔数：使用`LengthPrefix` + 业务校验 + `clearReceiveBuffer()`盲重置；
    - S7‑TPKT等带固定同步魔数：优先`Custom`模式，在splitter内部实现搜索同步标记重同步。
4. Custom模式下：模块只负责append新字节到buffer；**帧失步检测、重同步全部交由splitter业务代码，模块不做干预**。

## 六、文档&注释核查点
1. `clearReceiveBuffer()`注释写明：异步投递、不改动发送队列/wait‑ack、ack开启下的副作用。
2. `receiveBufferSize()`注释写明：异步快照，**仅诊断，禁止业务逻辑使用**。
3. 文档明确区分「正常半包」与「帧失步」，说明模块只提供工具原语，**可靠重同步属于上层业务责任，不存在通用内置重同步**。

## 七、风险场景复现验证点（给IDE，让它找潜在BUG路径）
> 场景：TCP连接不断开，但中间数据流损坏乱码，未触发maxFrameSize。
1. 此时只会进入“滑1字节”弱自愈路径；有可能切出虚假语法合法帧从`frameReceived`抛出，errorOccurred不一定报错，发生静默错位。
2. 模块不会自动修复，必须依靠上层业务校验发现 + 调用`clearReceiveBuffer()`止损。
> 要求：检查源码是否存在该风险路径，确认不会出现内部死循环、CPU空转。
