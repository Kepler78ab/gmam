# v0.0.3 — 接收缓冲与上层重同步

## 1. 问题

TCP 是字节流。拆帧缓冲头部若是**残片**（非合法帧起点），即便后面有完整业务帧，也可能长期错位，称为**帧失步**。  
模块内 LengthPrefix 仅有「非法长度滑 1 字节 / 超长清空」弱自愈，**不提供**协议级可靠 Resync。

本版约定：**可靠重同步由上层负责**；模块只提供清空/查询内部拆帧缓冲的手段。

## 2. 半包 vs 失步

| 状态 | 含义 | 模块 LengthPrefix 行为 |
|------|------|------------------------|
| 正常半包 | 缓冲头部是合法帧起点，仅字节不足 | 等待更多数据（正确） |
| 帧失步 | 缓冲头部是报文中间残片 | 无显式检测；可能误解析长度或滑字节 |

## 3. 本版 API

| 方法 | 语义 |
|------|------|
| `TcpClient::clearReceiveBuffer()` | **异步**清空拆帧缓冲与最近错误。不碰发送队列 / wait-ack / 连接。ack 开启时可能丢掉未匹配应答 → 超时重传（预期） |
| `TcpClient::receiveBufferSize()` | 跨线程**快照**，仅诊断；worker 未启动返回 0 |

**断开 / 重连何时 clear：**

| 时机 | 是否 clear |
|------|------------|
| `disconnected` / `slotDisconnect` | **否**（建议上层手动 `clearReceiveBuffer`） |
| 主动 `connectToHost` → `slotConnect` | **发起尝试前** clear；已 Connected/Connecting 则本次不清 |
| `onSocketConnected`（含自动重连连上） | **是** |
| 自动重连 `onReconnectTimeout` 发起时 | **否**（等连上成功再清） |
| `shutdown` | **是** |

**建议**上层在 `disconnected` 时手动 clear；勿误以为「调用了 `connectToHost` 就一定已清」或「只有连上成功才清」（主动再连在尝试前就会清）。

## 4. 上层接法

**A. Custom / Raw（推荐自管 Resync）**

- `Custom`：在 `setCustomFrameSplitter` 内校验、滑动、删除已消费字节。  
- `Raw`：听 `bytesReceived`，上层自建缓冲与重同步。  
此时模块缓冲为空或不用，`clearReceiveBuffer` 对 Raw 几乎无意义。

**B. LengthPrefix / PesAscii（模块切帧 + 上层止损）**

```text
frameReceived → 业务校验（长度自洽 / CRC / 电文号等）
  连续失败达 N → clearReceiveBuffer()
  （可选）短时丢弃后续帧直到出现合法同步特征
```

**C. 断开时建议上层手动清理**

模块不在 `disconnected` 自动 clear。**建议**业务在 `disconnected` 槽（或主动 `disconnectFromHost` 后）调用一次 `clearReceiveBuffer()`，避免残片滞留到重连前；重连成功路径仍会再 clear 一次（双保险）。

## 5. 明确不做

- 搜同步字、协议相关滑动算法  
- 「已失步 / 已重同步」专用信号  
- 改现有 LengthPrefix 弱自愈策略  
- **disconnected 时自动 clear**（交上层或依赖 connected 时 clear）
